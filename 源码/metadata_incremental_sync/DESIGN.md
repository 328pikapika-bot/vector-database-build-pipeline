# 每日元数据增量同步：方案草案与一致性限制

状态：已实现并通过本地模拟测试与 231 只读 Schema 核对（2026-10-20）。
新 Topic 使用 `VECTOR_JOURNAL_ARTICLE_METADATA_INCREMENTAL_IDS`，配置为 1 分区、
3 副本。231 的独立小集合已验证三个向量字段支持局部更新。当前未启动本项目对
`scientific_documents_v2` 的真实写入；Solr 只读预检查遇到 HTTP 503，需恢复后
再进行端到端验证。带 `_V1`、`_V2` 后缀的旧 Topic 已于 2026-10-20
按用户要求在确认无现存消息、无活跃消费者后清理；本项目只使用无版本后缀的 Topic。

## 已确认的目标

- 新 Kafka Topic 只投递文献 ID。独立 Worker 24 小时运行，收到 ID 后查询当时的 Solr；不等待、比较或证明 Solr 是否为最新版本。
- 每次从 Solr 结果生成同一份字段数据，并重新计算标题、摘要、关键词三个向量。已有 ID 更新，缺失 ID 插入。Solr 查不到整条文献时记录失败 ID，绝不据此删除 Milvus 记录。
- 目标是与 `scientific_documents_v2` 的 41 字段 Schema 对齐：原 24 字段（含三个向量）加 16 个历史补字段和 `entityType`。Schema 中存在字段不代表全部历史行已填值。
- 当前只连接 231 测试 Milvus：`default/scientific_documents_v2`。未来生产是三套独立 Milvus，三个目标各自保存一份完整数据；目标地址、数据库、集合和认证通过 Stack 配置，不写死在代码中。
- 保留当前存量补字段程序和状态。增量项目是独立目录、镜像、Stack、消费组和状态目录。不得删除、清空、重建现有集合或索引。

## 必须记录的限制：三套独立 Milvus 无跨库原子提交

业务期望是每个 ID 要么同时进入 A/B/C 三套 Milvus，要么三套都不改变；一套失败时记录 ID 以后再处理，Worker 本身不停止。

三套独立 Milvus 没有共同的 prepare/commit/rollback 事务。即使写入前全部通过健康检查，也可能 A、B 已写成功而 C 在写入时超时；并行发送、顺序发送或按批发送都不能消除这个窗口。把失败 ID 记入队列不能撤销已成功的写入；补偿性删除或回滚也可能失败，并会触碰历史数据保护边界。因此**不能承诺三套物理库在任何瞬间绝对相同**，也不能把“全局尚未成功”描述成“另两套从未写入”。

在保持三套独立的前提下，可实现的安全语义是：写前检查所有目标；若预先发现任一目标不可用，本 ID 一套都不写，持久化待处理记录；若写入途中出现部分成功，则持久化各目标状态、停止领取新的写入批次，优先把失败目标补至同一份数据，三套 Strong 读回核对后才标记该 ID 全局成功。Worker 在等待期间保持运行、报告状态并继续重试。该方案提供最终一致和可审计的全局确认，**不提供瞬时物理原子性**。

三目标正式启用属于单独的设计关口。在上述业务硬要求未调整或未更换为可提供所需事务语义的架构前，程序不得将三目标模式标称为“原子同步成功”；测试阶段只启用 231 单目标。

## 推荐实现方式

在仓库根目录使用本目录 `metadata_incremental_sync/`。只移植、固定并测试现有项目中确有必要的纯转换逻辑：

- 原 24 字段及三个向量的定义参考 `vector_sync_service/app/contracts/docx_contract.py`；Solr 查询和原字段转换参考 `vector_sync_service/app/services/solr_source.py`；向量文本准备及调用参考 `vector_sync_service/app/services/batch_processor_existing.py`、`embedder.py`。
- 16 字段来源与长度参考 `solr_field_backfill/field_mapping.json`；`entityType` 取 `stringIMS_entityType` 数组首元素，参考 `solr_field_backfill/entity_type_backfill.py`。
- Kafka 手动提交、分区撤销和有界消费可参考现有 `kafka_consumer.py`，但新 Worker 只处理文献元数据，不触碰全文、图片或其他集合。

不要直接复制旧 Worker 的整个运行入口：`independent_kafka_worker.py` 在 Solr 缺源时会构造 `DELETE`；`milvus_service.py` 的现有写法是完整记录 `upsert`。存量补字段程序则只填空值，不能直接用作增量覆盖程序。

计划的独立组件：Kafka ID 消费、Solr 读取与 41 字段映射、三向量生成、目标集合适配器、持久化待处理/失败账本、每日统计、健康与安全暂停、测试及容器文件。第一版 Stack 只配置 231 单目标；代码的目标配置结构预留多目标，但不默认启用三目标写入。

### 单目标写入规则

1. 启动时只读校验目标数据库、集合身份、主键、41 字段类型、三个向量维度和索引；Schema 不符即安全暂停，不自动建表、删表或改索引。
2. 只接受约定格式的 ID。每条 Kafka 消息以 Topic、partition、offset 建立幂等记录；先可靠保存待处理状态，再推进 Kafka offset。重放同一消息不能重复计数或丢任务。
3. Solr 只查询文献；查询不到则保存缺源 ID 和原因，不写 Milvus。Solr 或向量服务暂时不可用时持续退避重试，Worker 进程保持运行。
4. 一次查询形成一份规范化字段快照，并生成三个 2560 维向量。字段超长、类型不符或向量失败则记录该 ID，不提交不完整记录。
5. Strong 读取目标 ID。已有记录只提交主键、已确认来源的字段及新向量，通过 `partial_update=True` 更新；现有未返回的字段保留。新 ID 确认不存在后才插入符合完整 Schema 的记录。写入超时先 Strong 读回核对再决定重试。Milvus 的存在检查与插入不是跨请求原子操作，因此同一 ID 必须由一个写入者负责，不能与旧入库服务并发插入。验证 Milvus 当前版本对**三个向量字段的局部更新**确实有效，是接入真实集合前的硬性测试关口；若不支持，不得悄悄改用完整记录 upsert。
6. 对新增字段，Solr 明确返回的值覆盖；Solr 未返回时不清空已有值。`hasAuthor_str`、`hasSource_str`、`hasFile_str`、`hasCreateOrganization_str` 仍无确认来源，现有值必须保留，新记录可空。`id` 不变。
7. 更新后读回关键字段和向量核对，记录“新增、更新、无需变化、缺源、失败、待重试”。任何代码路径都不得调用 Milvus delete/drop/truncate，也不得对已有记录执行完整记录覆盖写入。

### Kafka、断点和日报

- 一个固定消费组消费新 Topic，关闭自动提交。单实例运行；用持久化账本保证容器异常退出和重启后可恢复。状态目录与日志目录独立挂载，不能覆盖应用代码。
- 运行状态区分：正常消费、等待 Solr/向量/Milvus、存储安全暂停、待人工处理。容器在等待依赖时继续运行并发送心跳；持久化状态无法保证时暂停领取新消息，不跳过 offset。
- 同一 ID 的事件按顺序处理，旧事件的迟到重试不能覆盖后一次事件。若 Topic 有多分区，建议生产者以文献 ID 作 Kafka key；仅消息体包含 ID 时，Worker 还须在账本中串行化同一 ID。
- Topic 没有“每日结束”消息。按首次收到 ID 至最后一条完成确认统计处理时间；Kafka 积压清零并连续空闲一段可配置时间后生成当日/当次窗口报告。报告分别显示接收、实际新增、实际更新、失败/待重试、开始/结束时间、处理耗时和速度；不能把暂时空闲说成上游明确宣布结束。

### 与存量任务并行的边界

现有 16 字段程序及 `entityType` 专项任务仍须保留，后续还要处理完整的 17 字段存量补齐。存量程序只填空值，增量程序刷新 Solr 值；同一 ID 并发写入会产生覆盖顺序竞争。存量程序还把固定逻辑记录数作为安全基线，新增 ID 会改变记录数。因此在两程序同写一个集合前，必须设计共享写入协调及可核对的新增记录计数，或安排互斥写入窗口；仅把两者放进不同容器不能解决该问题。这项协调单独实施并验证，不在本设计记录阶段改动旧程序。

## Stack 与生产迁移

- 镜像默认 `check`，测试 Stack 显式 `run`，目标仅 231。231 的现有部署使用外部 `milvus` 网络；以 Stack 所在 Docker 环境的实际连通性选 URI。凭据由 Portainer 环境变量/密钥提供，文件与日志不存明文。
- 同一镜像将来通过 Stack 配置目标列表；改变环境变量须更新并重新部署 Stack，单纯 Restart 不会装入新配置。测试与生产使用不同的消费组、持久化账本和报告目录，不复用 231 已提交的 offset。
- 三套生产 Milvus 必须先完成历史基线复制，并核对 Schema、三个向量维度/模型、索引、记录数和抽样哈希，再确定 Kafka 追赶起点；每日增量 Worker 不负责把 5,000 多万条历史数据复制为三份。
- 对三目标模式，配置校验必须明确呈现本文件所述原子性限制，不得因为在 Stack 填了三个地址就默认宣称满足“任一失败则其他两个绝不写入”。
